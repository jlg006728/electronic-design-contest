## 背景

现场现象：OpenMV 卡死/失效前，会先出现“OpenMV 灯仍随识别目标变化，但舵机不动”。这说明视觉识别本身不一定已经死掉，问题可能在 OpenMV UART 发出、MSPM0 接收/解析、或 MSPM0 控制更新路径。

## MSPM0 改动

只加诊断变量，不改变 HOME、方向和主要追踪逻辑。

当前 HOME 和方向：

```c
#define SERVO_X_HOME_US 850U
#define SERVO_Y_HOME_US 1500U
#define AIM_X_PULSE_SIGN (-1)
#define AIM_Y_PULSE_SIGN (-1)
```

新增 Watch 变量：

- `g_diag_stage`
- `g_diag_x_limited`
- `g_diag_y_limited`
- `g_diag_no_link_count`
- `g_diag_no_target_count`
- `g_diag_small_target_count`
- `g_diag_confirm_wait_count`
- `g_diag_deadband_count`
- `g_diag_servo_update_count`
- `g_diag_limited_count`

`g_diag_stage` 含义：

- `0`：链路超时/未收到有效帧
- `1`：收到 OpenMV 有效颜色帧
- `2`：收到帧但无目标
- `3`：目标像素太小，被 MSPM0 拒收
- `4`：目标确认等待中
- `5`：目标在死区内，所以舵机不动
- `6`：已更新舵机命令
- `7`：舵机命令触及软件限位

## OpenMV 改动

新脚本不再让 `uart.any()` 决定是否执行视觉循环：

- 每轮都执行 `sensor.snapshot()`、颜色识别、主动串流。
- UART RX 只做清空和标记，不再执行命令应答路径。
- 关闭周期性 `print`，减少无 USB 独立供电时的阻塞风险。

## 现场判断

如果 OpenMV 灯还会随目标变，但舵机不动：

- `g_omv_color_frame_count` 不增加：OpenMV 识别还在，但 MSPM0 没收到有效颜色帧，查 UART/GND/J21/J22。
- `g_omv_color_frame_count` 增加，`g_diag_stage=3`：目标太小，被 MSPM0 拒收。
- `g_omv_color_frame_count` 增加，`g_diag_stage=5`：目标在死区，舵机不动是正常的。
- `g_omv_color_frame_count` 增加，`g_diag_stage=6` 但舵机不动：查舵机供电/信号/PWM/机械。
- `g_diag_stage=7`：舵机软件限位卡住。
